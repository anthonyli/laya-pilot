# Architecture / 架构

LayaPilot targets enterprise admin applications, especially table, filter, form and CRUD workflows. The architecture prioritizes accurate assertions, predictable execution and local or intranet inference. Approvals, permission matrices and file-transfer workflows require explicit adapters and validation before they can be treated as supported enterprise features.

The public runner exposes execution and generation. Execution through `--excel` detects workbook format before opening a browser: ordinary cases use the natural-language engine, generated workbooks retain structured replay and integrity checks. The legacy `--mode execute` command remains compatible. Internally, there are three paths: `generate` and `execute` in `scripts/lib/workflow.mjs`, and natural-language workbook execution in `scripts/lib/engine.mjs`. `scripts/worker.py` imports spreadsheets through `openpyxl` and performs local Laya decisions when requested. API decisions use `scripts/lib/model.mjs`; the API key remains in the environment or a hidden prompt. Browser initialization is centralized in `scripts/lib/browser-provider.mjs`.

The browser session currently exposes a Playwright `browser`, `context`, and `page`. A new browser backend must implement the page operations used by `scripts/lib/dom.mjs`, `scripts/lib/form.mjs`, `scripts/lib/readiness.mjs`, `scripts/lib/workflow.mjs`, and `scripts/lib/engine.mjs`, plus context tracing and diagnostic events. Merely accepting `--browser-provider browser-use` would be misleading; the runner rejects it until an adapter and integration tests exist.

The decision boundary is `choose(state, criteria, meta)`, returning a choice among the supplied candidates and calibrated probabilities or an explicit failure. Local Laya and the currently compatible HTTP API implement this behavior. A future Jev API adapter needs an explicit request/response mapping, probability validation, credential handling and contract tests before it can be selected.

Generation keeps the CRUD templates, but field semantics and option groups now pass through Laya even when a rule could select them. Data recipes retain symbolic run identifiers for reproducible replay. Explicit fixture data remains an override. Natural-language Excel target matching and semantic-step fallback remain in `dom.mjs` and `planner.mjs`.

Workflow replay also grounds action targets through Laya, including a unique matching control. `scripts/lib/replay-model.mjs` matches recorded form fields against live candidates; it rejects different choices rather than replacing test inputs. Saved option paths use exact matching after the field decision. DOM ownership/scope guards and deterministic assertions remain mandatory. `replay-target` decisions and model/cache metrics make this participation observable.

After templates, the `discover` operation derives bounded candidates from observed search/reset controls, form cancellation, email types and numeric min/max attributes. Laya can accept or skip each candidate; assertions remain deterministic and replay uses model target grounding. The `assert-discovery` workbook grammar rejects unsupported actions and never submits a form. This is not an unrestricted business-test planner. Unsupported observed workflows and skipped candidates remain visible in the report. Generation exports all attempts to `执行结果.xlsx`, independently of the verified-only replay workbook.

The workbook contract is in `scripts/lib/workflow_excel.py`. The visible 17 columns are human readable; `__laya_steps__` contains a structured, validated replay plan. The digest binds the visible case ID, title, preconditions, steps and expected result to the plan. The generated Excel is a test artifact, not arbitrary executable code.

Current UI coverage is strongest for semantic HTML plus Ant Design, Element and TNTD conventions. A new component family should extend observation and form rules, then add a browser fixture test. Keep company-specific selectors, URLs, credentials and data preparation in a separate private adapter repository rather than this public core.

`scripts/lib/auth-state.mjs` restores origin/account-bound storage and validates an authenticated page marker before saving. `scripts/lib/run-state.mjs` journals workflow cases and pre-dispatch write intent using atomic JSON replacement and a per-directory lock. `scripts/lib/workflow-policy.mjs` checks allowed operations and read-only replay steps before browser startup. These are runtime boundaries, not a replacement browser-driver contract. The CLI preloads local Laya alongside browser setup and waits for readiness before business steps; `--lazy-model` opts out. API providers receive no warmup requests. Pure assertions do not request decisions; replay actions use the ready model, with identical requests eligible for the in-process cache. Integration fixtures run through the real CLI and Chromium with `npm run test:browser`, explicitly using lazy mode to avoid a dependency on model weights.

## Skill packaging

The repository root is the skill root: `SKILL.md`, optional `agents/`, `references/`, `assets/`, and `scripts/` provide the entrypoint and resources; all execution code lives in `scripts/`, including `lib/`, `runner.mjs`, `worker.py`, and `demo-server.mjs`. The API-first skill launcher and legacy CLI share that code. `scripts/package_skill.py` builds an allowlisted ZIP under `dist/`, with the same paths and dependency manifests as the repository. It never synchronizes a second runtime tree into Git. Generated content hashes live only in the distribution manifest. `npm run skill:check` compares the built ZIP with current sources.

Installed upgrades replace distribution-owned files and preserve configuration, authentication state, Python environments, dependencies, and models. An old manifest allows obsolete `runtime/` source files to be removed; unlisted files remain untouched. Rerun setup after upgrading to install Node dependencies at the new root location.

The skill uses only `.env.local` plus explicit command-line overrides. Setup creates no JSON configuration, and the launcher ignores leftover `config.local.json` files. The underlying runner retains explicit `--config` support for legacy integrations; the skill entrypoints do not expose it. API remains the skill default, and local inference and write authorization require explicit CLI choices.
